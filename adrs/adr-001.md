## 1. Context
In standard Virtual Production setups, real-time engines frequently process technical inputs (e.g., MIDI, DMX, OSC, Live Link) directly inside concrete device logic or Blueprint actors. This tight coupling makes device abstractions rigid, prevents seamless hardware swapping, and conflates semantic business logic with transport-level protocol parsing. The framework requires an entity model that remains completely decoupled from physical hardware protocols.

---

## 2. Decision
The `StudioObject` acts exclusively as an **Aggregate Root** modeling the semantic business state of a production entity. It encapsulates generic attributes and sub-models:
* `StudioIdentity` (Immutable Value Object)
* `StudioRole` (Domain classification)
* `StudioLifecycle` (Deterministic state machine)
* `StudioCapabilitySet` (Functional contracts)

All communication with physical hardware, external protocols, or runtime drivers is handled strictly by modular, decoupled **Implementation Components** (`StudioComponent`) attached to the `StudioObject`.

---

## 3. Consequences
* **Positive:** Complete hardware-agnosticism. A virtual engine light actor and a physical DMX ARRI SkyPanel share the identical `StudioObject` representation.
* **Positive:** High reusability, modular composition, and isolated unit testability of the semantic layer.
* **Positive:** Zero protocol logic inside core domain classes.
* **Negative:** Slight architectural overhead, requiring communication to route through the component adapter layer rather than direct hardware access.
